## Correctness and security review before treating workflows as complete

The following are source-review concerns and unfinished contracts, **not reproduced test failures**. Verify against current code and add targeted regression checks while fixing them.

- [ ] **Staff scope:** event-wide `score` capability currently lets scorers act without assignment checks. Add assigned-match enforcement to both reads and mutations; revoke permissions on subsequent requests.
- [ ] **Invalid input boundaries:** `int(...)`, UUID parsing, direct `request.POST[...]`, and some ORM lookups can raise raw exceptions. Return appropriate validation/not-found/conflict responses without exposing internals or producing a 500 for ordinary bad input.
- [ ] **Mutation guards:** commands decorated with `services.command` lock the event, check revisions/idempotency, and gate closed events; several direct view mutations do not have equivalent protections. Review court/settings/staff actions and all new handlers.
- [ ] **Consent versions:** token redemption and `accept_partner` must bind acceptance to the policy actually displayed and accepted. `EntryMember.policy_version` currently comes from entry creation; policy changes between invitation and acceptance need explicit treatment.
- [ ] **Participant identity/counting:** `register` checks `event.participants.count() + len(people)`, which can reject reuse of existing participants at the ceiling. Count genuinely new unique people, and preserve server-side identity/duplicate guards.
- [ ] **Registration completion:** verify expired/withdrawn partner invitations, waitlist fairness, simultaneous last-spot admission, and capacity-hold consumption. `advance_waitlist` presently runs only during certain commands; timed maintenance is missing.
- [ ] **Retirement evidence:** the score form/validator currently only records completed games. The spec requires preserving an incomplete game separately when a player retires.
- [ ] **Correction dependencies:** `descendants_of` follows explicit elimination edges. Pool results also determine playoff qualifiers; changing a pool result after playoffs are generated must invalidate/block affected qualification instead of leaving inconsistent playoff entries.
- [ ] **Double elimination and byes:** test all supported entrant counts, especially non-power-of-two draws and two-entry tournaments; verify loss destinations and that the final reset activates only when required.
- [ ] **Standings:** check tie criteria, administrative outcomes, withdrawn entries, provisional/final presentation, and final placements with published fixtures. Elimination standings do not assign unsupported lower places.
- [ ] **Scheduling:** current proposals handle resolved `ready` matches. They do not plan unresolved future bracket matches or fully forecast event completion. Test shared people across divisions, actual overruns, rest, buffers, availability, active reservations, and infeasible windows.
- [ ] **Manual scheduling:** the service can commit intervals, but accessible manual assignment/pinning controls are not complete. Add them with the same revision and conflict checks.
- [ ] **Court holds:** decide and document how a blocked court affects an already active/suspended match; avoid allowing a restart that bypasses the hold.
- [ ] **Archived/final state:** correction, cancellation, partial results, archiving, and financial follow-up need consistent guards and visible state. A dedicated partial-results workflow and some lifecycle controls remain unfinished.
- [ ] **Public privacy:** test HTML, live JSON, CSVs, archives, links, and role-specific views. Never reuse private roster serialization for public responses. Review `live()` for unresolved/admin-outcome edge cases.
- [ ] **Authentication:** test single-use token redemption, non-consuming GET previews, expiry, scoped participant sessions, invite revocation, rate limits, private events, and the loopback-only demo/mailbox boundary.
- [ ] **Idempotency/concurrency:** use real transaction tests for admission, calls/starts, result confirmation, lost-response replay, and correction. SQLite immediate transactions and PostgreSQL row locks require their own evidence.
- [ ] **Audit/revisions:** retain immutable result/draw snapshots and trace all material changes; exclude private participant text and secrets from audit payloads.
